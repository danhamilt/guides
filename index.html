AI in Your Editor

An agent inside VS Code, wired to DeepSeek, connected to GitHub — plus what gists are actually good for. Aimed at developers who have been writing code for years and are new to the AI tooling, not at people learning to code.

VS Code / VSCodium + Cline DeepSeek — pay per token, ~$5 to start GitHub + gists covered October 2026

1. The mental model

Before the tooling, the part that actually changes how you work.

An AI editor is not autocomplete with a personality. It is a loop: the model reads context, proposes a change, you approve it, and it applies the change across files and runs commands. Everything else is configuration.

Diagram 1 — Autocomplete suggests tokens. An agent runs a loop. You own step 3.

The five terms worth internalising

Agent loopRead context → plan → act (edit files, run commands) → observe → repeat, until done or you stop it.
Plan vs ActPlan mode is read-only and can't touch files. Act mode executes. Start in Plan unless the task is trivial.
ContextWhat the model can see right now: your open files, files you attach, and rules files. It does not magically know your codebase.
Rules file.clinerules/ in the repo — persistent instructions, version-controlled alongside the code. Treated as code, because it is.
Tokens & costYou pay per million tokens in and out. Long context costs, but re-read context is discounted. Cost tracks what you feed it.
The one mindset shift

Treat it as a fast, tireless junior who has read everything and remembers nothing between sessions unless you write it down. It is excellent at mechanical breadth — refactors across 40 files, tests, boilerplate, diffs you'd rather not read line by line — and unreliable on subtle intent. The rules file is how you stop repeating yourself.

2. Setup

Four steps. Roughly ten minutes, most of it waiting on downloads.

1. VS Code

If you don't already have it, install from code.visualstudio.com. Nothing novel here — it is the same editor, now with an agent bolted on.

2. The Cline extension

Extensions panel (Ctrl/Cmd+Shift+X) → search Cline → Install. It adds a robot icon to the activity bar; that panel is your agent.

Being a VS Code extension rather than a fork is the point: your keybindings, extensions, settings, and git workflow all keep working. The alternatives are Cursor (a fork, and DeepSeek is no longer built in) or the cline CLI if you want the same agent in a terminal or CI.

3. A DeepSeek key

Sign up at platform.deepseek.com (separate from the consumer chat site). Add a small amount of credit under Billing — a key with a zero balance fails on every call, which is the most common first-day error. Then API Keys → Create and copy it once; it is never shown again.

Store it in your password manager, not a dotfile you might commit.

4. Wire them together

In the Cline panel: settings → API Provider: DeepSeek → paste the key → model deepseek-flash. Open a project folder and give it a throwaway task to confirm the round trip.

The model-name trap

Older builds and most tutorials still list deepseek-chat and deepseek-reasoner. Both were retired on 24 July 2026 and now fail. The live names are deepseek-flash and deepseek-v4-pro. If the dropdown is stale, type the name in by hand.

3. Editors & alternatives

VS Code is only the host. The substance is Cline plus a cheap model, and Cline runs in several editors — so if you dislike VS Code, you are not stuck with it.

If you want Cursor's agent window specifically

That layout — code on one side, an agent chat panel on the other, with plans, inline diffs, and approve buttons — is Cursor's agent. You can have exactly that layout, driven by DeepSeek, on Cursor's free plan, by putting Cline inside Cursor.

The restriction in the next subsection applies to Cursor's own agent asking for a Pro subscription. It does not apply to a third-party extension doing the work with your own key. So:

  1. Install Cursor (free) from cursor.com.
  2. Extensions panel (Ctrl/Cmd+Shift+X) → search Cline → Install.
  3. In Cline's settings: API Provider: DeepSeek → paste your key → model deepseek-flash.

You now have the editor and the window you wanted, and Cline — not Cursor's metered agent — is what spends your DeepSeek key. No Cursor Pro required.

The window is the same everywhere

Cline's panel looks and behaves the same in VS Code, VSCodium, Cursor, JetBrains, and Zed. So "an agent chat beside the code" is the shared experience; the host is mostly cosmetic. Pick whichever editor you will actually keep opening — and if that is Cursor, use it, just let Cline drive.

VSCodium — same editor, fewer Microsoft bits

VSCodium is VS Code built from the same open-source repo, minus Microsoft's telemetry, branding, and license. It is not easier than VS Code; it is the same editor, and day to day you will not notice a difference except that nothing phones home.

Cline explicitly supports it and ships on Open VSX, so the install is the same flow: Extensions → search Cline → install. What you give up is the Microsoft Marketplace — VSCodium uses Open VSX instead, which is smaller and missing some extensions that are licensed to the official build (Remote Development, some debuggers, Copilot, assorted Microsoft extensions). Occasionally Open VSX rate-limits and the extension search fails on a fresh install; retry, or install a .vsix by hand.

Cursor — the polished option, and the honest answer on free + DeepSeek

The short answer as of October 2026 is effectively no, for three reasons:

  • BYOK is Pro-only for the features that matter. Using your own key with Agent, Composer, Edit, and Ask requires a Pro subscription. It briefly worked on Free as an undocumented option, and that is now closed — the "you've hit your usage limit" message people hit is really a subscription check.
  • Custom keys are documented for chat models only. Tab completion always runs on Cursor's own models, regardless of your settings.
  • Agent is a separate lane. Cursor's Agent and Composer run on its own proprietary models, and whether a BYOK DeepSeek key drives the full agent loop is undocumented, with mixed community reports at best.

So "Cursor free" means Cursor's own models, not DeepSeek's cheap tokens. If you want Cursor's own agent on DeepSeek, budget $20/mo or use the 14-day Pro trial. If what you actually want is the layout, skip that and use the Cline path above — same window, your key, no subscription. DeepSeek as a chat-pane extra in Cursor is base URL https://api.deepseek.com/v1, model deepseek-v4-pro.

If it is the UI you dislike, this will not help

Cursor is itself a VS Code fork — same layout, same keybindings, same muscle memory. VSCodium removes the Microsoft parts but keeps the UI identical. If you genuinely want a different editor, the options that actually feel different are JetBrains and Zed, both of which Cline supports.

Where else Cline runs

Cline is not VS Code-specific. The same extension runs in Cursor, VSCodium, Windsurf, and JetBrains IDEs, with an ACP integration for editors such as Zed and Neovim. If you already live in IntelliJ or PyCharm, you do not have to move editors at all. The cline CLI shares the same agent core — same Plan/Act, rules, and MCP configuration across every surface. Pick the host you will actually keep using; it does not change the workflow.

Do not over-optimise the host

The host is the least interesting decision here. The value comes from Cline, a committed .clinerules/, a cheap model, and the habit of reading the plan before approving it. Any of these editors gets you there; spending a week choosing between them does not.

4. Working with it

The difference between a useful agent and an expensive autocomplete is how you drive the loop.

Plan first, and mean it

Plan mode cannot touch files. Use it to have the model survey the codebase and propose an approach you can argue with, before anything changes. For anything cross-cutting, /deep-planning forces a longer planning pass and produces a plan it can then work against.

Give it a rules file, and commit it

.clinerules/ at the repo root (global at ~/.cline/.clinerules) is the highest-leverage ten minutes you'll spend. It reads every .md and .txt in there, and it also picks up AGENTS.md, .cursorrules, and .windsurfrules, so you can share conventions across tools. A rule file can be scoped with YAML frontmatter so it only activates on matching paths:

# .clinerules/01-style.md
---
paths: ["src/**/*.ts"]
---
- Follow existing patterns in the repo before inventing new ones.
- No new dependencies without asking.
- Every new function gets a test.
- Prefer small, reviewable diffs over one large rewrite.

# .clinerules/02-git.md
- Never commit or push. Stage nothing. I do that myself.
- Do not reformat files you were not asked to change.

Because rules are just files, you can ask the agent to edit them: "Refine the git rule to also forbid amending published commits." Rules live in version control and get reviewed like anything else.

Control the blast radius

  • Small tasks, small diffs. One concern per session beats a giant prompt. The diff is the deliverable and you have to read it.
  • Checkpoints. Cline takes snapshots, so you can roll back a bad turn without touching git.
  • Read the plan before approving execution. This is the whole safety story. Everything else is convenience.
  • Let git be the backstop. Work on a branch. If a run goes sideways, git diff tells you exactly what happened.

5. The GitHub integration

Three layers: auth built into VS Code, an extension for PRs and issues, and the CLI for automation.

Diagram 2 — Issue to PR. The agent can be anywhere in this chain; the approval stays with you.

Sign in

Git clone, fetch, pull, and push work with no extension — VS Code prompts you to authenticate with GitHub the first time you touch a private repo or push. For pull requests and issues, install the GitHub Pull Requests and Issues extension, then sign in from the GitHub icon in the activity bar. The GitHub Repositories extension lets you browse and edit a repo without cloning it, which is handy for a quick look at someone else's code.

Pull requests and issues in the editor

Once signed in you get a sidebar of PRs and issues (waiting for your review, assigned to you, created by you — all configurable). Checkout a PR to review it locally, comment inline, and create PRs with GitHub Pull Requests: Create Pull Request from the command palette. A nice touch: Start working on issue creates the branch for you, ready for the agent to work in.

The CLI, for anything scriptable

The gh CLI is the glue. Cline can call it directly, and it is the sane way to drive GitHub from an agent because it is already authenticated and its output is parseable.

gh pr list --search "review-requested:@me"
gh pr checks 1234
gh pr diff 1234
gh pr view 1234 --json title,body,files
gh issue create --title "Cache invalidation on logout" --body "..."

Automated PR review in CI

Cline ships as a CLI and runs headless in GitHub Actions, which makes a genuinely useful review bot. Install the CLI with npm i -g cline (Node 20+), then in a workflow give it the PR number, a GH_TOKEN, and a scoped command allowlist so it can read the diff but not do anything destructive:

env:
  GH_TOKEN: ${{ github.token }}
  CLINE_COMMAND_PERMISSIONS: |
    { "allow": [
      "gh pr diff *", "gh pr view *", "gh pr checks *",
      "gh issue view *", "git log *",
      "gh pr comment *"
    ] }
run: |
  cline --yolo 'Review this PR for logic errors, edge cases,
  security issues, and adherence to repo conventions. Post a summary.'

Headless mode also triggers on a pipe or a redirect, which makes one-off scripting trivial: git diff | cline "review these changes". Useful flags: --json for NDJSON you can pipe, -p to start in Plan, --thinking to dial reasoning effort.

Two real operational gotchas

The gh hang: Cline can stall indefinitely waiting for gh to signal completion. The fix is to switch Terminal Execution Mode to Background Exec in Cline's Advanced settings, which bypasses VS Code's shell integration.

MCP approval: reported behaviour where write-capable MCP tools can execute without an approval prompt even when auto-approve is off. If you attach MCP servers that can write — post comments, open PRs — keep their permissions tight and don't rely on the UI toggle as a security boundary.

6. GitHub gists

A gist is a single-file (or few-file) git repository with a web UI. It is a URL, not a project.

What a gist actually is

Every gist is a real git repo: it has history, it can be forked, cloned, and versioned. What it lacks is everything a repo has around it — no issues, no pull requests, no file tree, no README on the landing page. That constraint is the feature. It is the lightest possible way to put a snippet, a config file, a script, or a document at a URL.

Diagram 3 — Public vs secret, and why the raw URL won't render HTML on its own.

Creating and managing them

From the web: gist.github.com, fill in a filename with an extension (syntax highlighting follows it), and choose Create secret gist or Create public gist. From the CLI, which is faster and scriptable:

# Secret by default. Add --public to list it publicly.
gh gist create --public script.py -d "quick thing"

# Several files in one gist, or read from stdin / a pipe
gh gist create notes.md refs.txt
pbpaste | gh gist create --filename snippet.txt

# Manage the lifecycle
gh gist list
gh gist view <id> --raw
gh gist edit <id> --filename script.py        # edit in $EDITOR
gh gist edit <id> --filename script.py local.py  # replace from a file
gh gist edit <id> --add extra.md --remove old.md
gh gist clone <id>            # it is a git repo; clone it
gh gist rename <id> old.md new.md
gh gist delete <id>

Public vs secret, precisely

Secret does not mean private. A secret gist is omitted from Discover and search, but anyone with the URL can read it. Treat it as unlisted, not confidential, and never paste a credential into one. Two rules to internalise: you cannot convert a public gist back to secret, but you can promote a secret gist to public by editing it.

Gist, repo, or Pages?

You want to…Use
Share one file or a small snippet at a URLGist
Keep history on a scratch file without a repoGist
Collaborate, review, track issuesRepository
Publish a document or a working web pageRepo + GitHub Pages

Using a gist to publish a page

This is the trick worth knowing, and it is how this guide could have been shared: GitHub serves gist content as text/plain, so a …/raw/… URL shows your HTML source rather than rendering it. Put it behind a CDN proxy and it renders as a real page:

# raw URL (shows source, not a page)
https://gist.githubusercontent.com/<user>/<id>/raw/index.html

# same file, rendered — prefix a CDN that sets text/html
https://cdn.statically.io/gist/<user>/<id>/raw/index.html

Handy for a quick one-file demo or a write-up. For anything that should stay up and be maintained, use a repo with GitHub Pages instead — a gist is a URL, a Pages site is a site.

Embedding a gist

Grab the <script src="https://gist.github.com/<user>/<id>.js"></script> snippet from any gist and drop it into a page to embed the file with syntax highlighting. Good for docs, blog posts, and wikis.

7. Prompting patterns that actually work

You already know how to specify work precisely. The trick is aiming it at something with no memory and a fixed context window.

Plan before code
Read the auth module and the three callers that depend on it. Propose a plan to move token refresh into a middleware, list every file you would touch, and flag anything that could break. Do not change anything yet.
Scope it to a diff you can review
Refactor only src/billing/invoice.ts. Do not reformat or touch other files. Keep the public function signatures identical. When done, show me a summary of the diff, not the whole file.
Make it explain before you trust it
Before you edit anything, explain in two sentences what this function currently does and what you believe is wrong with it. Then wait for my confirmation.
Ask it to find the seams
Summarise this repo for someone who has just inherited it: the entry points, the data flow, what looks fragile, and the three files to read first. Cite file paths. Ask me if two places contradict each other.
Have it argue against you
Here is my design for the retry strategy. Argue the strongest case against it, name the assumption most likely to be wrong, and tell me what test would falsify it.
Get it to write the test first
Write a failing test that captures the behaviour described in this ticket. Do not implement the fix yet. Show me the test so I can confirm it tests the right thing.
The pattern underneath

Name the scope, the constraints, and the output shape; demand a plan before edits; and ask it to flag its own uncertainty separately from the answer. That last instruction is what stops a confident fabrication reaching a pull request.

Never put a credential in a gist

A secret gist is unlisted, not private. The same goes for the agent's context: anything you attach or paste leaves your machine and is processed by the provider. Keys, tokens, customer data, and anything under NDA stay out of both.

Verify anything that reaches a PR

It produces plausible numbers, dates, and API details with total confidence. The diff is the artifact you are accountable for — read it the way you would read a junior's pull request, which is exactly what it is.
